# Deploying Odysseus

How to get from `localhost` to *your phone, on mobile data, driving the agent on
your PC*.

---

## The shape of it

```
   your phone / any browser                your workstation
            │                                     │
            │ HTTPS + WSS                         │ WSS (dialled OUT)
            ▼                                     ▼
   ┌────────────────────┐              ┌──────────────────────┐
   │  Frontend (Vercel) │─────────────▶│  Control Plane       │◀────┐
   └────────────────────┘   API/WS     │  (Render, Docker)    │     │
                                       └──────────────────────┘     │
                                                                    │
                                          the gateway keeps this ───┘
                                          socket open from your PC
```

**Your PC never accepts an inbound connection.** The gateway dials out and
commands travel back down the socket it opened. No port forwarding, no dynamic
DNS, no public IP, no ngrok. Your router is untouched, and this works the same
on home WiFi, a café hotspot or a phone hotspot.

Only two things get deployed: the **Control Plane** and the **frontend**. The
gateway stays on your machine, because that is where the code, the agent CLIs
and your credentials are.

---

## Which host — and why Render

| | Render | Fly.io | Railway |
|---|---|---|---|
| Free tier | **Yes** | No | No |
| Long-lived WebSockets | Yes | Yes | Yes |
| Sleeps when idle | Yes (~15 min) | No | No |
| Setup effort | Lowest | Medium | Low |

**Start on Render.** It is the only one of the three with a genuinely free tier,
it runs persistent web services with native WebSocket support, and `render.yaml`
in this repository is a complete blueprint — you point Render at the repo and it
builds.

The free tier sleeps after ~15 minutes with no inbound traffic. In practice that
matters less than it sounds: a connected gateway heartbeats every 15s, so the
service stays awake while you are using it. When your workstation is off it
sleeps, and on the next connection it cold-starts in about a minute — the
gateway's reconnect is capped at 20s with unlimited retries, so it comes back on
its own. A sleeping Control Plane is a delay, not an outage.

**Move to Fly.io when the latency starts to matter.** `odysseus/fly.toml` is
ready: pick a region near you, `auto_stop_machines = false`, and there is no
cold start. Budget a few dollars a month.

**Do not put the Control Plane on Vercel** — or Netlify Functions, or Lambda.
Not a limitation to work around: serverless has no persistent process to hold a
socket open, and this architecture *is* a persistent socket. The frontend on
Vercel is fine and expected.

> Hosting terms change. The table reflects the state as of this writing —
> check the current free-tier terms before you commit.

## Step 1 — Persistence (Firebase)

The Control Plane **refuses to start in production without a database.** The
in-memory store is correct for tests and wrong for a container, because hosted
platforms restart routinely and every restart would erase users, paired devices,
sessions and the audit log.

1. Create a Firebase project and enable **Cloud Firestore**.
2. Project Settings → Service Accounts → **Generate new private key**.
3. From that JSON you need three values: `project_id`, `client_email`,
   `private_key`.

## Step 2 — Deploy the Control Plane

Render Dashboard → **New** → **Blueprint** → select this repository. It reads
`render.yaml`. Then set the variables marked `sync: false`:

| Variable | Required | Value |
|---|:-:|---|
| `JWT_SECRET` | ✅ | Generated by Render. Do not rotate casually — it logs everyone out. |
| `CORS_ORIGINS` | ✅ | The **exact** origin of your frontend, e.g. `https://odysseus.vercel.app`. No trailing slash. |
| `USE_FIRESTORE` | ✅ | `true` |
| `FIREBASE_PROJECT_ID` | ✅ | from the service account JSON |
| `FIREBASE_CLIENT_EMAIL` | ✅ | from the service account JSON |
| `FIREBASE_PRIVATE_KEY` | ✅ | the full key, including `-----BEGIN PRIVATE KEY-----` |
| `SECURE_COOKIES` | ✅ | `true` (defaults true when `NODE_ENV=production`) |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | — | Web Push. Generate with `npx web-push generate-vapid-keys`. |
| `CREDENTIAL_ENCRYPTION_SECRET` | — | Generated by Render. Encrypts stored third-party credentials. |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` / `GITHUB_CALLBACK_URL` | — | GitHub integration. |

**If you get any of these wrong, the service will not start** — it exits 78
(`EX_CONFIG`) and prints every problem at once:

```
Refusing to start in production with an insecure configuration:
  1. JWT_SECRET is not set. The development default is published in this repository...
  2. CORS_ORIGINS is not set, so it defaults to localhost and your deployed frontend will be rejected...
  3. No persistent database is configured...
```

That is deliberate. A Control Plane that boots with an insecure config looks
exactly like one that is fine, and nobody re-reads a warning in a deploy log.

You now have `https://odysseus-control-plane.onrender.com` (your name will
differ). Check it:

```bash
curl https://odysseus-control-plane.onrender.com/health
```

## Step 3 — Deploy the frontend

Deploy `frontend/` to Vercel. Set:

```
NEXT_PUBLIC_API_URL=https://odysseus-control-plane.onrender.com
NEXT_PUBLIC_WS_URL=wss://odysseus-control-plane.onrender.com
NEXT_PUBLIC_AUTH_PROVIDER=local
```

Two things that will bite you:

- **`wss://`, not `ws://`.** A page served over HTTPS cannot open a `ws://`
  socket — browsers block mixed content outright. The page loads fine and is
  silently realtime-dead.
- Go back and set `CORS_ORIGINS` on Render to this frontend's exact origin.
  A mismatch shows up as a CORS error that looks like a frontend bug.

## Step 4 — Pair your workstation

On your PC:

```bash
cd odysseus
CONTROL_PLANE_URL=https://odysseus-control-plane.onrender.com pnpm pair
```

It prints a code and a fingerprint. Open the web app on your phone, enter the
code, and **check the fingerprint words match what your terminal printed** —
that is the out-of-band step that makes pairing meaningful rather than a code
you type on faith.

Pairing registers your device's public key. Everything the gateway sends from
then on is signed with the matching private key, which never leaves your
machine.

## Step 5 — Run the gateway

```bash
cd odysseus
ODYSSEUS_CONTROL_PLANE_URL=wss://odysseus-control-plane.onrender.com/ws/tunnel pnpm gateway
```

Or persist it in `~/.odysseus/config.yaml`:

```yaml
controlPlane:
  url: wss://odysseus-control-plane.onrender.com/ws/tunnel
  autoConnect: true
projectRoots:
  - C:\your\project
```

Config precedence is flags > environment > file > defaults. Check what it
resolved to without starting anything:

```bash
pnpm gateway --print-config
```

Open the web app on your phone. Your workstation should show as online.

## Security model

What changed to make public exposure safe:

**The gateway proves it holds a private key.** Authentication is a
challenge-response: the gateway signs its identity, the server replies with a
random single-use challenge bound to that socket, and the gateway signs that
too. Signatures are verified against the public key registered at pairing time
— never against a key presented in the request, which an attacker controls.

This matters because **device ids are not secrets.** They appear in API
responses, in the UI and in logs. Previously, knowing one was enough to register
as somebody's workstation.

Also enforced:

- Replayed auth payloads are rejected (single-use nonces, ±120s timestamp window)
- A device whose stored record has no public key is refused with an error telling you to re-pair, rather than being trusted
- The browser WebSocket requires a valid JWT — an absent token is refused exactly like an invalid one
- WebSocket upgrades are Origin-checked against the CORS allowlist (browsers do not apply CORS to WebSocket handshakes, so this is a separate gate against Cross-Site WebSocket Hijacking)
- Pairing-code verification is rate limited per user

### What is still open

Stated plainly, because a deployment guide that only lists strengths is not
useful:

- **The browser client has no heartbeat and no event replay on reconnect.** Put your phone in your pocket and take it out, and the timeline resumes live with a silent gap. The backfill endpoint (`GET /api/v1/sessions/:id/events?fromSequence=N`) exists; the client does not yet call it. This is phase N4.2 in [CHAPTER_3_GOING_ONLINE.md](CHAPTER_3_GOING_ONLINE.md).
- **Neither WebSocket server pings its clients**, so a dead browser socket is never reaped.
- **No PWA manifest**, so the app cannot be installed to a home screen.
- **Nothing here has been exercised against a real deployed host yet.** The idle-timeout numbers and cold-start behaviour above are read from documentation and code, not measured.

## Notes on the build

**The image runs TypeScript through `tsx` rather than compiled output.** This is
deliberate and worth knowing: every workspace package exports `./src/index.ts`,
so `node dist/server.js` would resolve sibling packages back to TypeScript
source and fail at runtime. `tsx` is a pinned dependency, not an `npx` fetch, so
the version is deterministic.

Moving to compiled output means adding a `production` export condition to all
~18 workspace packages and running node with `--conditions=production`. Worth
doing eventually; not worth coupling to a security fix.

The image still runs `tsc --build` during the build stage, so a type error fails
the image rather than the container.

### Running it locally

```bash
cd odysseus
docker build -t odysseus-control-plane .
docker run -p 4000:4000 -e NODE_ENV=development odysseus-control-plane
```

## CI

`.github/workflows/ci.yml` runs on every push and PR:

- **Typecheck** (`tsc --build`) — blocking
- **Lint** — reporting only, because of 16 pre-existing `no-unsafe-*` errors in two files. Gating on them would make main red on arrival.
- **Tests** — blocking
- **Docker image builds** — blocking, so a broken Dockerfile is caught before Render finds it mid-deploy
- **Secret scan** (gitleaks) — blocking

Render auto-deploys from `main`, so main staying green is what keeps the hosted
Control Plane working.
