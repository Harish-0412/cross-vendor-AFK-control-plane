# Deploying Odysseus

How to get from `localhost` to _your phone, on mobile data, driving the agent on
your PC_.

---

## The shape of it

```
   your phone / any browser                your workstation
            │                                     │
            │ HTTPS + WSS                         │ WSS (dialled OUT)
            ▼                                     ▼
   ┌────────────────────┐              ┌──────────────────────┐
   │  Frontend (Vercel) │─────────────▶│  Control Plane       │◀────┐
   └────────────────────┘   API/WS     │  (Render, Docker)    │     │
                                       └──────────────────────┘     │
                                                                    │
                                          the gateway keeps this ───┘
                                          socket open from your PC
```

**Your PC never accepts an inbound connection.** The gateway dials out and
commands travel back down the socket it opened. No port forwarding, no dynamic
DNS, no public IP, no ngrok. Your router is untouched, and this works the same
on home WiFi, a café hotspot or a phone hotspot.

Only two things get deployed: the **Control Plane** and the **frontend**. The
gateway stays on your machine, because that is where the code, the agent CLIs
and your credentials are.

---

## Which host — and why Render

|                       | Render        | Fly.io | Railway |
| --------------------- | ------------- | ------ | ------- |
| Free tier             | **Yes**       | No     | No      |
| Long-lived WebSockets | Yes           | Yes    | Yes     |
| Sleeps when idle      | Yes (~15 min) | No     | No      |
| Setup effort          | Lowest        | Medium | Low     |

**Start on Render.** It is the only one of the three with a genuinely free tier,
it runs persistent web services with native WebSocket support, and `render.yaml`
in this repository is a complete blueprint — you point Render at the repo and it
builds.

The free tier sleeps after ~15 minutes with no inbound traffic. In practice that
matters less than it sounds: a connected gateway heartbeats every 15s, so the
service stays awake while you are using it. When your workstation is off it
sleeps, and on the next connection it cold-starts in about a minute — the
gateway's reconnect is capped at 20s with unlimited retries, so it comes back on
its own. A sleeping Control Plane is a delay, not an outage.

**Move to Fly.io when the latency starts to matter.** `odysseus/fly.toml` is
ready: pick a region near you, `auto_stop_machines = false`, and there is no
cold start. Budget a few dollars a month.

**Do not put the Control Plane on Vercel** — or Netlify Functions, or Lambda.
Not a limitation to work around: serverless has no persistent process to hold a
socket open, and this architecture _is_ a persistent socket. The frontend on
Vercel is fine and expected.

> Hosting terms change. The table reflects the state as of this writing —
> check the current free-tier terms before you commit.

## Step 1 — Persistence (Firebase)

The Control Plane **refuses to start in production without a database.** The
in-memory store is correct for tests and wrong for a container, because hosted
platforms restart routinely and every restart would erase users, paired devices,
sessions and the audit log.

1. Create a Firebase project and enable **Cloud Firestore**.
2. Project Settings → Service Accounts → **Generate new private key**. This
   downloads a JSON file.

## Step 2 — Deploy the Control Plane (Render)

Render Dashboard → **New** → **Blueprint** → select this repository. It reads
`render.yaml`.

**Give it the Firebase key as a Secret File, not as pasted env vars.** On the
service: **Environment → Secret Files → Add Secret File**:

- Filename: `firebase-service-account.json`
- Contents: paste the whole downloaded JSON file

Render mounts it at `/etc/secrets/firebase-service-account.json`. Then set:

| Variable                         | Value                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `GOOGLE_APPLICATION_CREDENTIALS` | `/etc/secrets/firebase-service-account.json`                                                                |
| `USE_FIRESTORE`                  | `true`                                                                                                      |
| `CORS_ORIGINS`                   | the **exact** frontend origin, e.g. `https://odysseus-control-center.vercel.app` — no trailing slash |
| `SECURE_COOKIES`                 | `true`                                                                                                      |
| `JWT_SECRET`                     | generated by the blueprint; do not rotate casually, it logs everyone out                                    |

Why a file: a multi-line private key pasted into an env var is the classic way
to break PEM newlines, and it spreads the key into more places than it needs to
be. The file goes from your disk to Render and nowhere else.

Optional: `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` for Web Push
(`npx web-push generate-vapid-keys`), and the `GITHUB_*` variables for the GitHub
integration.

**If anything is wrong, the service will not start** — it exits 78 (`EX_CONFIG`)
and prints every problem at once. If Firestore cannot load, the log now says
which credential sources it checked and which were missing.

Check it:

```bash
curl https://odysseus-control-plane.onrender.com/health
```

## Step 3 — Deploy the frontend (Vercel)

Vercel → **Add New → Project** → import this repository:

- **Root Directory:** `frontend`
- **Include files outside the root directory:** on (the default)
- Framework: Next.js (auto-detected)

Environment variables (Production):

```
CONTROL_PLANE_URL=https://odysseus-control-plane.onrender.com
NEXT_PUBLIC_API_PROXY=true
NEXT_PUBLIC_WS_URL=wss://odysseus-control-plane.onrender.com
NEXT_PUBLIC_AUTH_PROVIDER=local
```

**Why the proxy.** The frontend and the Control Plane are on different sites
(`vercel.app` vs `onrender.com`). The refresh-token cookie, set cross-site, is
not sent on `fetch` — and Safari blocks it outright as a third-party cookie. So
`/api/v1/*` is rewritten through the Vercel domain (`next.config.mjs`), which
makes the cookie first-party. Without it every reload logs you out, and on an
iPhone login never sticks at all.

WebSockets cannot go through the proxy and do not need to: they authenticate
with the access token. That is why `NEXT_PUBLIC_WS_URL` points straight at
Render — and why it must be **`wss://`**: a page served over HTTPS cannot open a
`ws://` socket.

The frontend origin must match `CORS_ORIGINS` on Render exactly, because
WebSocket upgrades are Origin-checked against it.

> The first request after Render has been asleep takes about a minute while it
> cold-starts. Through the proxy that can surface as a timeout — retry once.

### Grant the first Firebase owner safely

The admin console accepts roles from a **verified Firebase Authentication
custom claim**, not from a browser-supplied value or a Firestore document
field. In a trusted server-side Firebase Admin script (never in the browser),
set either the preferred namespaced claim or the backwards-compatible claim:

```ts
await getAuth().setCustomUserClaims(firebaseUid, { odysseusRole: 'owner' });
// Existing deployments may instead use: { role: 'owner' }
```

Allowed values are `user`, `admin`, and `owner`. The Control Plane writes the
verified value into its own user record and continues authorizing every
admin request from that durable record. On the next visit to `/admin`, the web
app forces an ID-token refresh, so a newly assigned role works without waiting
for Firebase's normal token rotation. If it still does not, sign out and back
in once and confirm Render has the Firebase Admin credentials for the same
Firebase project.

When an owner changes a role in the Odysseus **Users** console, that platform
decision becomes authoritative; a stale Firebase token cannot reverse it.

## Step 4 — Pair your workstation

Run these on the PC that has your code. Environment variables are set
differently per shell — **`VAR=value command` is bash syntax and fails in
PowerShell** with "The term ... is not recognized".

**PowerShell (Windows):**

```powershell
cd "C:\SideQuest\AI Coding Agent AFK Control Plane\odysseus"
$env:CONTROL_PLANE_URL = "https://odysseus-control-plane.onrender.com"
$env:ODYSSEUS_WEB_URL  = "https://odysseus-control-center.vercel.app"
pnpm pair
```

**bash / macOS / Linux:**

```bash
CONTROL_PLANE_URL=https://odysseus-control-plane.onrender.com \
ODYSSEUS_WEB_URL=https://odysseus-control-center.vercel.app \
pnpm pair
```

It prints a pairing code and a set of fingerprint words, then waits (5 min).
On your phone or browser:

1. Open the web app and **register** (first time) or log in.
2. Go to **Devices → Pair**, enter the code.
3. **Check the fingerprint words match the terminal exactly** before
   confirming. That comparison is what makes pairing meaningful: it proves the
   device you are trusting is the one in front of you.
4. Confirm. The terminal prints `Pairing confirmed!`.

Pairing registers this machine's public key. From then on the gateway proves
its identity by signing a server challenge; the private key never leaves
`~/.odysseus`.

> If Render has been asleep, the first request takes about a minute. If
> `pnpm pair` says it cannot reach the Control Plane, wait and run it again.

## Step 5 — Run the gateway

**PowerShell:**

```powershell
cd "C:\SideQuest\AI Coding Agent AFK Control Plane\odysseus"
$env:ODYSSEUS_CONTROL_PLANE_URL = "wss://odysseus-control-plane.onrender.com/ws/tunnel"
pnpm gateway --project-root "C:\path\to\your\project"
```

**bash:**

```bash
ODYSSEUS_CONTROL_PLANE_URL=wss://odysseus-control-plane.onrender.com/ws/tunnel \
  pnpm gateway --project-root /path/to/your/project
```

`--project-root` is the repository the agent is allowed to work in; repeat it
for more than one. The gateway only serves the roots you list.

To avoid setting the variable every time, put it in `~/.odysseus/config.yaml`
(on Windows: `C:\Users\<you>\.odysseus\config.yaml`):

```yaml
controlPlane:
  url: wss://odysseus-control-plane.onrender.com/ws/tunnel
  autoConnect: true
projectRoots:
  - C:\path\to\your\project
```

Precedence is flags > environment > file > defaults. Check what it resolved to
without starting anything:

```powershell
pnpm gateway --print-config
```

A healthy start logs the device identity, each detected agent, and then
`auth_success` once the signed handshake completes. Open the web app on your
phone — the workstation shows as **online**, and you can start a session.

Which agent it drives depends on what is installed. OpenCode and Claude Code
have adapters; on Windows both are npm `.cmd` shims, which the adapters resolve
to the real executable (never via a shell — the prompt is an argument, and a
shell would make it injectable). If detection still fails, point at the binary
directly with `OPENCODE_BINARY`.

## Security model

What changed to make public exposure safe:

**The gateway proves it holds a private key.** Authentication is a
challenge-response: the gateway signs its identity, the server replies with a
random single-use challenge bound to that socket, and the gateway signs that
too. Signatures are verified against the public key registered at pairing time
— never against a key presented in the request, which an attacker controls.

This matters because **device ids are not secrets.** They appear in API
responses, in the UI and in logs. Previously, knowing one was enough to register
as somebody's workstation.

Also enforced:

- Replayed auth payloads are rejected (single-use nonces, ±120s timestamp window)
- A device whose stored record has no public key is refused with an error telling you to re-pair, rather than being trusted
- The browser WebSocket requires a valid JWT — an absent token is refused exactly like an invalid one
- WebSocket upgrades are Origin-checked against the CORS allowlist (browsers do not apply CORS to WebSocket handshakes, so this is a separate gate against Cross-Site WebSocket Hijacking)
- Pairing-code verification is rate limited per user

### What is still open

Stated plainly, because a deployment guide that only lists strengths is not
useful:

- **The browser client has no heartbeat and no event replay on reconnect.** Put your phone in your pocket and take it out, and the timeline resumes live with a silent gap. The backfill endpoint (`GET /api/v1/sessions/:id/events?fromSequence=N`) exists; the client does not yet call it. This is phase N4.2 in [CHAPTER_3_GOING_ONLINE.md](CHAPTER_3_GOING_ONLINE.md).
- **Neither WebSocket server pings its clients**, so a dead browser socket is never reaped.
- **No PWA manifest**, so the app cannot be installed to a home screen.
- **Nothing here has been exercised against a real deployed host yet.** The idle-timeout numbers and cold-start behaviour above are read from documentation and code, not measured.

## Notes on the build

**The image runs TypeScript through `tsx` rather than compiled output.** This is
deliberate and worth knowing: every workspace package exports `./src/index.ts`,
so `node dist/server.js` would resolve sibling packages back to TypeScript
source and fail at runtime. `tsx` is a pinned dependency, not an `npx` fetch, so
the version is deterministic.

Moving to compiled output means adding a `production` export condition to all
~18 workspace packages and running node with `--conditions=production`. Worth
doing eventually; not worth coupling to a security fix.

The image still runs `tsc --build` during the build stage, so a type error fails
the image rather than the container.

### Running it locally

```bash
cd odysseus
docker build -t odysseus-control-plane .
docker run -p 4000:4000 -e NODE_ENV=development odysseus-control-plane
```

## CI

`.github/workflows/ci.yml` runs on every push and PR:

- **Typecheck** (`tsc --build`) — blocking
- **Lint** — reporting only, because of 16 pre-existing `no-unsafe-*` errors in two files. Gating on them would make main red on arrival.
- **Tests** — blocking
- **Docker image builds** — blocking, so a broken Dockerfile is caught before Render finds it mid-deploy
- **Secret scan** (gitleaks) — blocking

Render auto-deploys from `main`, so main staying green is what keeps the hosted
Control Plane working.
